# IMP-020: FMI2 Model Field Type Corrections (value_reference, start, unit, ModelStructure)

## Status

Proposed

## Layer

Domain Model / Codec (FMI2)

## Theme

FMI2 dataclass and codec type fidelity

## Evidence

### Current state in `pyssp_standard/standard/fmi2/model/model_description.py`

**`Fmi2ScalarVariable`** (lines 48-58):

```python
@dataclass
class Fmi2ScalarVariable:
    name: str
    value_reference: str         # ← FMI 2.0 specifies integer; typed as str
    type_name: str
    description: str | None = None
    causality: str | None = None
    variability: str | None = None
    initial: str | None = None
    declared_type: str | None = None
    start: str | None = None     # ← FMI 2.0 allows float for Real types; typed as str only
    type_attributes: dict[str, str] = field(default_factory=dict)  # ← 'unit' is buried here
```

- `value_reference` is typed as `str` but FMI 2.0 (section 4.2.4) defines it as an integer attribute. All standard consumers need `int` for comparison, mapping, and serialization.
- `start` is typed as `str` but for Real/Integer types it should be a numeric value. FMI 2.0 defines `start` as a numeric attribute whose type depends on the variable's declared type.
- `unit` is not a dedicated field — it lives in `type_attributes` dict alongside `min`, `max`, etc. Every consumer must check `sv.type_attributes.get("unit")` instead of `sv.unit`.

**`Fmi2Unknown`** (lines 33-37):

```python
@dataclass
class Fmi2Unknown:
    index: str                   # ← FMI 2.0 defines integer 'index' attribute
    dependencies: str | None = None       # ← FMI 2.0 defines as space-separated list of ints
    dependencies_kind: str | None = None  # ← FMI 2.0 defines as space-separated list of strings
```

- `index` is typed as `str` but FMI 2.0 section 2.3.2 defines `<Unknown index="N">` where N is an integer.
- `dependencies` is typed as `str | None` (e.g., `"1 2 3"`) but represents a list of value references.
- `dependencies_kind` is typed as `str | None` (e.g., `"dependent constant"`) but represents a list of enum values.

### Current codec (`pyssp_standard/standard/fmi2/codec/model_description_xml_codec.py`)

- `_parse_variables` (lines 173-201): reads `valueReference` as string from XML attribute; assigns to `value_reference: str` field.
- `_parse_unknown_group` (lines 212-222): reads `index` as string; assigns to `index: str` field. Reads `dependencies` and `dependenciesKind` as raw strings.
- Serialization writes these string values back as-is.

### Current tests (`pytest/fmi2/codec/test_model_description_xml_codec.py`)

All assertions on `value_reference` and `index` use string values:
```python
assert reparsed.variables[0].value_reference == "1"    # line 52-54
assert reparsed.model_structure.outputs[0].index == "1"  # line 143
```

### Current project consumers (confirmed by the cs-fmu-packager external spec)

The cs-fmu-packager project (and likely all other FMU consumers) must manually parse `valueReference` from XML via `int(scalarvariable_element.attrib["valueReference"])` because the typed model only offers it as a string. This undermines the entire purpose of the typed model layer.

## Current Pain Or Risk

1. **Forced consumer-side parsing**: Every project that needs `value_reference` as `int` must parse the XML themselves or convert from `str`. The typed model abstraction is leaky.
2. **Lost type safety**: Python type checkers cannot detect misuse. A comparison like `sv.value_reference == 42` is valid Python but fails at runtime because it's comparing `str == int`.
3. **Non-Real `start` values hidden**: `start` being typed only as `str` loses semantic information. The codec stores non-Real `start` values correctly as strings in the XML, but downstream consumers can't distinguish "no start set" (`None`) from "start is a string" (e.g., for `Enumeration`).
4. **`unit` ergonomics**: Callers accessing `sv.type_attributes.get("unit")` discoverability is poor compared to `sv.unit`. Non-Real types (Integer, Boolean, String, Enumeration) with `unit` attributes are silently hidden in `type_attributes`.
5. **`Fmi2Unknown` structure ambiguity**: Consumers must manually parse `dependencies` and `dependencies_kind` from space-separated strings, repeating the same split/parse logic across every project.
6. **Serialization inconsistency**: The codec's `_append_unknown_group` already serializes these with `_set_optional(..., unknown.dependencies)` which works with strings but would also work with properly typed values via a formatting step.

## Proposed Improvement

**Phase 1 — `Fmi2ScalarVariable` type corrections:**

1. Change `value_reference` type from `str` to `int` on `Fmi2ScalarVariable`.
2. Change `start` type from `str | None` to `str | float | None` (float for Real/Integer numeric values, str for non-numeric types like Enumeration).
3. Add `unit` as `str | None` field on `Fmi2ScalarVariable` (extracted from `type_attributes` during parsing, removed from `type_attributes` dict to avoid duplication; or kept accessible via both paths).

**Phase 2 — `Fmi2Unknown` type corrections:**

4. Change `index` type from `str` to `int`.
5. Change `dependencies` type from `str | None` to `list[int]`.
6. Change `dependencies_kind` type from `str | None` to `list[str]`.

**Phase 3 — Codec adaptations:**

7. Update `_parse_variables`: convert `valueReference` attribute to `int`; convert `start` to `float` for Real types and keep as `str` for non-numeric; extract `unit` from type element attributes into dedicated field.
8. Update `_parse_unknown_group`: convert `index` to `int`; parse `dependencies` as space-separated `list[int]`; parse `dependencies_kind` as space-separated `list[str]`.
9. Update serialization methods to convert back to string representation for XML output.

**Phase 4 — Test adjustments:**

10. Update assertions in `pytest/fmi2/codec/test_model_description_xml_codec.py` to use `int` comparisons instead of `str`.
11. Update assertions in `pytest/fmi2/facade/test_model_description_fmi2.py` to use `int` comparisons.
12. Add test for `unit` field extraction.
13. Add test for `start` typed as `float` vs `str` vs `None`.
14. Add edge-case test for missing optional dependencies string (should produce `[]`, not `[""]`).

## Expected Benefit

- **Leaky-abstraction closed**: Consumers get proper types from the model layer. No manual XML parsing needed for these fields.
- **Type safety**: Static type checkers catch mismatches. No `str == int` surprises.
- **Discoverability**: `sv.unit` replaces `sv.type_attributes.get("unit")`.
- **FMI specification fidelity**: The model layer matches the FMI 2.0 specification's type definitions.
- **Consumer simplification**: The cs-fmu-packager and comparable projects can remove their manual XML parsing for `value_reference`, `start`, `unit`, and `ModelStructure` dependencies.
- **Serialization round-trips preserved**: Codec handles conversion between typed Python and string-based XML transparently.

## Risk And Blast Radius

| Risk | Severity | Mitigation |
|------|----------|------------|
| Breaking existing consumers of `Fmi2ScalarVariable.value_reference` as str | **High** — API break | This is an intentional API improvement. Impact limited to projects that import from `standard/fmi2/model/` directly. The `pyproject.toml` version bump should indicate breaking changes. The `ModelDescription` facade consumers are unaffected (they access `.xml` which returns the typed document). |
| `start` type change from `str|None` to `str|float|None` may widen existing str-only logic | Medium | Most consumers treat `start` as opaque anyway. Float comparison (`x.start == 1.0`) is more useful than string comparison. String consumers can use `str(x.start)` or `str(x.start) if x.start is not None else None`. |
| Missed dependencies parse for empty/absent attributes | Medium | `dependencies=""` should produce `[]` not `[""]`. Must handle `None` and empty string in parsing. |
| `unit` could appear in both `type_attributes` and dedicated field | Low | Document that `unit` is moved to dedicated field; may optionally keep in `type_attributes` for backward compat. |
| FMI3 is already correct | None | FMI3 model uses `value_reference: int`, `Unknown.value_reference: int` with `list[int]` for dependencies. No changes needed. |

## Suggested Priority

**High** — Incorrect types in the core FMI2 model layer cause every consumer to work around them. This is a data-fidelity issue, not just an ergonomic one. The type errors cascade into leaky abstractions across the entire library surface. Comparable to a P0 in the external spec.

### Implementation order:

1. Change model dataclasses first (no codec changes yet — tests will fail).
2. Update codec parser/serializer.
3. Update tests (last — confirms everything works end to end).

### Edge cases to test:

- `dependencies` absent → `[]`
- `dependencies` empty string → `[]`
- `dependencies` single value `"3"` → `[3]`
- `dependencies` multiple values `"1 2 3"` → `[1, 2, 3]`
- `dependencies_kind` absent → `[]`
- `start` as float (`"1.5"`) → `1.5`
- `start` as int string (`"42"`) → `42.0` (float, per FMI 2.0 Real type)
- `start` as non-numeric string (Enumeration) → keep as `str`
- `start` absent → `None`
- `unit` present on Real → `sv.unit == "N"`
- `unit` present on Integer → `sv.unit == "N"`
- `unit` absent → `sv.unit is None`
