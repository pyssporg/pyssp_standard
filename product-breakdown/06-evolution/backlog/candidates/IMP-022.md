# IMP-022: Deterministic ZIP Timestamps for Reproducible Archive Builds

## Status

Proposed

## Layer

Archive

## Theme

Reproducible archive packaging with deterministic timestamps

## Evidence

### Current archive packing in `pyssp_standard/common/archive.py`

The `_write_archive_file` function (lines 32-39) uses `ZipInfo.from_file()`:

```python
def _write_archive_file(archive: zipfile.ZipFile, path: Path, arcname: str) -> None:
    info = zipfile.ZipInfo.from_file(path, arcname=arcname)
    info.compress_type = zipfile.ZIP_DEFLATED
    if _is_library_path(arcname):
        info.external_attr = _zip_external_attr(_with_executable_bits(path.stat().st_mode))
    with path.open("rb") as source:
        archive.writestr(info, source.read())
```

`ZipInfo.from_file()` sets the ZIP entry's date_time from the underlying file's modification time (`os.path.getmtime`). This means:

- **In CI**: Git checkout timestamps vary per run (unless git's `core.checkStat` is configured). Each CI run produces a different ZIP SHA256 hash, even for identical content.
- **In local development**: File modification times depend on when files were checked out or generated.
- **For cross-platform CI**: Different platforms may report different mtimes for extracted archives.

The `package_archive` function (lines 175-229) uses `_write_archive_file` for every file entry. No timestamp normalization occurs.

### Current `ArchiveRuntime._commit()` (`pyssp_standard/common/archive_runtime.py`, lines 71-72)

```python
def _commit(self) -> None:
    package_archive(self.root, self.path, recursive=True)
```

No timestamp options are passed through.

### Current `FMU.package_as_ssp()` (`pyssp_standard/fmu.py`, lines 48-77)

No timestamp control is available. The generated SSP archive receives whatever timestamps the filesystem provides.

### Current `SSP.add_fmu()` and `SSP.__enter__` (`pyssp_standard/ssp.py`)

These create archives without explicit timestamp management.

### Current tests

No tests verify ZIP hash stability across repeated serializations.

### External evidence

The cs-fmu-packager project (author of the external specification) intentionally skipped migrating `packager.py` to the fork's API because non-reproducible ZIP hashes would break CI comparison workflows.

```python
# cs-fmu-packager currently does:
# (manual ZIP creation with fixed timestamps to ensure reproducible builds)
```

FMI Cross-Check Guidelines and CI environments benefit from reproducible archives:
- CI can cache based on content hash
- FMU fingerprinting/comparison is possible
- Git-tracked generated FMUs produce stable diffs

## Current Pain Or Risk

1. **Non-reproducible builds**: Same source content produces different ZIP files on each run. CI workflows cannot compare FMU outputs by hash.
2. **Skipped migration**: The cs-fmu-packager skipped using the fork's archive layer because of this issue. Other archive consumers face the same blocker.
3. **No explicit API**: There is no `date_time` parameter on `package_archive()`, no `fixed_timestamp` option, and no way to pass `ZipInfo.date_time` control from `FMU.package_as_ssp()` or `SSP.add_fmu()`.
4. **CI cache invalidation**: Non-deterministic timestamps invalidate content-based caches. Every CI run re-packages all FMUs even when source content hasn't changed.
5. **FMICrossCheck compliance**: While not strictly required, deterministic timestamps are a best practice for reproducible FMU exchange.

## Proposed Improvement

### Phase 1 — Add timestamp parameter to `_write_archive_file`

```python
_DEFAULT_FIXED_TIMESTAMP = (2000, 1, 1, 0, 0, 0)  # FMI "zero" date

def _write_archive_file(archive, path, arcname, date_time=None):
    info = zipfile.ZipInfo.from_file(path, arcname=arcname)
    if date_time is not None:
        info.date_time = date_time
    info.compress_type = zipfile.ZIP_DEFLATED
    ...
```

### Phase 2 — Add timestamp parameter to `package_archive`

```python
def package_archive(
    source_dir, archive_path, *, recursive=False, overwrite=True,
    fixed_timestamp: tuple[int, int, int, int, int, int] | None = None,
) -> Path:
```

When `fixed_timestamp` is provided, all entries use the same timestamp. When `None` (default), behavior is unchanged for backward compatibility.

### Phase 3 — Thread timestamp control through `ArchiveRuntime`

```python
class ArchiveRuntime:
    def __init__(self, path, mode="r", fixed_timestamp=None):
        ...
    
    def _commit(self):
        package_archive(self.root, self.path, recursive=True, fixed_timestamp=self._fixed_timestamp)
```

### Phase 4 — Add constants and convenience for FMI default timestamp

```python
# In pyssp_standard/common/archive.py or a new constants module
FMI_EPOCH = (2000, 1, 1, 0, 0, 0)  # FMI 2.0 "zero" date used by many tools
```

### Phase 5 — Coverage and integration testing

5. Add test for ZIP hash stability with fixed timestamp
6. Add test for backward compatibility (existing behavior unmodified when `fixed_timestamp=None`)
7. Add test for `package_archive` producing identical hash on two calls with same source and fixed_timestamp

## Expected Benefit

- **Reproducible builds**: Same source content → same ZIP hash, every time.
- **CI enablement**: CI pipelines can verify "FMU unchanged" by content hash.
- **Consumer migration unblocked**: The cs-fmu-packager can migrate to the fork's archive runtime with deterministic timestamps.
- **Backward compatible**: `fixed_timestamp=None` preserves existing behavior for all current consumers.
- **Simple API**: Single optional tuple parameter; defaults to no-change.
- **Cross-platform consistency**: Fixed timestamps eliminate platform variation in ZIP entries.

## Risk And Blast Radius

| Risk | Severity | Mitigation |
|------|----------|------------|
| Breaking existing callers of `_write_archive_file` (internal only) | None | Internal function; all callers in same module; signature change is additive with default. |
| Breaking existing callers of `package_archive` (public API) | Low | Additive parameter with default `None`. Existing callers don't need modification. |
| Breaking `ArchiveRuntime.__init__` | Low | Additive parameter through `create_runtime`. Default `None` for backward compat. |
| FMI Cross-Check expectations for ZIP timestamps | Low | The FMI standard does not mandate specific ZIP timestamps. Fixed timestamps are compatible. |
| Performance impact | None | Setting `info.date_time` is trivially cheap (tuple assignment). |
| ZipInfo.date_time is a tuple of ints, not a datetime | Low | Use a simple 6-element tuple per Python's `zipfile.ZipInfo.date_time` format: (year, month, day, hour, minute, second). The `FMI_EPOCH` constant documents the standard choice. |

## Suggested Priority

**Low** — Functional correctness is not affected. All existing features work. This is a build reproducibility and CI optimization. The only concrete impact is that the cs-fmu-packager project's migration is blocked, but that's an external project concern. Comparable to P3 in the external spec.

## Out Of Scope

- **Deterministic ZIP for `.fmu` archives inside `.ssp`** — the recursive packaging already calls `package_archive` which would pass `fixed_timestamp`. If threaded through correctly, nested archives are covered.
- **Non-archive file operations outside `package_archive`** — e.g., `unpack_archive` reads ZIP timestamps but does not modify them.
- **Per-file custom timestamps** — single fixed timestamp is sufficient for reproducibility. Per-file control adds complexity without demonstrated need.
- **DateTime/parser integration** — No need for full datetime parsing. The tuple format matches `ZipInfo.date_time` directly.
- **Metadata signature validation** — deterministic timestamps do not affect FMU signing/validation.
- **IMP-020 or IMP-021 changes** — pure archive layer change, independent of FMI2 model/codec improvements.

## Notes

- The default `FMI_EPOCH = (2000, 1, 1, 0, 0, 0)` matches the FMI 2.0 "zero" date convention used by many FMU-generating tools (Dymola, OpenModelica). This is a well-known convention in the FMI ecosystem.
- Python 3.10+ `ZipInfo.from_file` preserves the file mtime. Setting `info.date_time` overrides this. The implementation must set `date_time` after `from_file`, not before.
- If `fixed_timestamp` is `None`, the current `from_file` mtime behavior is preserved unchanged.
- The `_write_archive_file` function in `archive.py` is the single bottleneck for all ZIP entry creation in the library. Adding the parameter there covers all code paths automatically.
